# Правила для агентов — Claude и Codex

> Один файл на всех. Claude читает его через `CLAUDE.md` (`@AGENTS.md`), Codex — напрямую.
> Правки правил — только сюда, чтобы у двух агентов не разошлись версии.
> Карта кода — `HANDOFF.md` (вверху — блок «Состояние»), лаборатория — `ASSET_LAB.md`.

## 1. Кто и как

- Общение с Денисом — по-русски. Денис — художник, не программист: технические
  решения агент принимает сам, спрашивает только про художественное.
- Движок — прежде всего авторский, художественный инструмент: инженерные
  решения принимают специалисты. Штамп не нужен. Нужны обмен с AutoCAD (DWG и
  DXF, с 3D и точными размерами) и спецификации в движке. Альбом Денис верстает
  в отдельной программе Negrita VOL 1 (замена InDesign).
- `publishedHomeSceneSettings.js` — авторская работа Дениса. Не переписывать руками,
  не откатывать. Новые ключи попадают туда только через пайплайн публикации
  (редактор «В проект» или `sanitizeHomeSceneSettingsForPublish(getPublishedHomeSceneSettings())`).
- Интерфейс редактора и лаборатории (стиль, расположение, подписи) не менять без
  прямой просьбы. Новые контролы — в существующем стиле, с подписями RU и EN.
- `git push` — только по просьбе. `main` на GitHub — это живой сайт.
- Этот репозиторий открытый. Адреса и порты серверов, ключи, настройки шлюза
  и туннелей сюда не класть. CMS (Payload) и серверные настройки с 2026-09-26 —
  в закрытом `DenisDaraganGarden/ddg-content-platform`; здесь остаётся только
  контракт манифеста портфолио (`schemas/portfolio-manifest.schema.json`,
  `src/features/portfolio-content/`, резерв `public/content/`).
- Проверки (`npm run check:*`, `smoke`) в обычной работе — по просьбе Дениса.
  Перед push или «На сайт» — минимум `npm run lint && npm run build`, а перед
  push кода — ещё `npm run check:fast` (все проверки без браузера, полторы
  минуты; то же гоняет GitHub). Сайт выкладывается только после них
  (`deploy-pages.yml`), поэтому проверка проверяет движок, а не авторские
  значения: где она берёт опубликованную сцену, нужные для теста числа
  подставляются поверх, чтобы любая сцена Дениса проходила.

## 2. Начало сессии — знать состояние

```bash
npm run handoff
```

Печатает ветку и последний коммит, отставание от `origin/main`, незакоммиченное,
stash, ветки с незалитыми коммитами, воркдеревья и занятые порты.

Прежде чем решить, что что-то «пропало» или «не сделано», проверить все места,
где может лежать работа: `git log --oneline main..origin/main`, `git branch --no-merged main`,
`git worktree list` (воркдеревья Codex — `.claude/worktrees/*`), `git stash list`.
Был случай: свободные камеры «исчезли», а на деле лежали в неслитой ветке.

## 3. Конец сессии — оставить след

- Закоммитить работу или явно оставить незакоммиченной — и в обоих случаях
  обновить блок «Состояние» в начале `HANDOFF.md`: последний коммит, что не
  закоммичено, что дальше. «Состояние» — только то, что верно сейчас, а не
  дневник: свою запись переписать, отжившую перенести в
  `docs/archive/handoff-log-2026.md` (там же летопись до 26.09.2026).
- Работа в воркдереве не считается сделанной, пока не слита в `main` или не
  описана в «Состоянии».
- Для изменений сцены «влито» означает также перенос согласованных настроек
  через публикацию и проверку результата в главном dev и на сайте. Один merge
  кода не включает объект: проверить его параметры в корне и снимках камер.
  Сохранять остальные авторские настройки и камеры; тестовые настройки целиком
  из песочницы не переносить. Перед принятием публикации в главном dev сравнить
  его текущую сцену с исходной, чтобы не затереть новые правки Дениса.
- Временные скрипты, скриншоты и заметки удалить; перед коммитом посмотреть
  `git status`, чтобы в публичный репозиторий не ушло лишнее.

## 4. Порты — карта и законы

Номера из незанятого диапазона 412xx; записи — в `.claude/launch.json` с `cwd: "."`
(работают из любого чекаута, включая воркдеревья). Порты не переименовывать и не
перенумеровывать без прямой просьбы: к ним привязаны кнопки запуска и черновики.

| Запись | Порт | Что это | Чьё |
|---|---|---|---|
| `site` | **41211** | dev-сервер, главная `/` | Дениса — смотреть его глазами |
| `editor` | **41212** | главный dev-редактор, `http://localhost:41212/home/edit` | Основная рабочая среда Дениса |
| `sandbox` | **41213** | тот же редактор, отдельный origin | Агента — здесь можно ломать |
| `dist` | **41214** | `vite preview` собранного `dist/` | Общий, только чтение |
| `lab` | **41215** | лаборатория ассетов `asset-lab.html` | Общий: смотреть и крутить ползунки можно всем, черновика сцены тут нет |
| `landscape` | **41218** | редактор портфолио `/landscape/` (`scripts/landscape/editor.mjs`) | Дениса — пишет в `public/landscape` и `src/data/landscapePortfolio.json` |
| `app` | **41219** | Electron-оболочка движка (`npm run app`): окно приложения + его сервер | Кнопка в списке запуска; вкладка панели на этом порту — зеркало меню проектов, само приложение — в своём окне. Установленное OUROBOROS.app — только из копии `~/Ouroboros/engine` (§5.1) |
| — | 4173 | внутренний порт смоук-теста (`SMOKE_PORT`) | Никогда не занимать вручную |

1. **Главный dev и сохранённые настройки — разные понятия.** 41212 — основной
   dev-редактор проекта; не называть сам сервер «черновиком». Настройки редактора
   сохраняются в `localStorage` отдельно для каждого origin (протокол, имя хоста,
   порт). `localhost` и `127.0.0.1` тоже имеют разные хранилища. Сохранять точный
   адрес рабочей среды, не подменять его адресом песочницы.
2. **Агент работает только в `sandbox` (41213)** или через свежий профиль
   Playwright (свой origin-storage, любой порт безопасен). В 41211/41212 агент
   заходит только смотреть, не трогая ползунки.
3. **Обмен сценой — только через публикацию**: «В проект» пишет
   `publishedHomeSceneSettings.js`, Денис забирает кнопкой «Откатить».
   Никогда через копирование localStorage. «На сайт» делает то же и сразу коммитит
   файл и пушит `HEAD:main` — агент её не нажимает без просьбы. Если в ветке
   сервера есть коммиты, которых нет на `origin/main`, «На сайт» отказывает
   (`scripts/deployScene.mjs`, `npm run check:deploy`).
4. **Смоук-тест требует машину целиком**: перед `npm run smoke` остановить все
   dev-серверы. «Не видно» при работающих серверах — конкуренция за GPU, а не регрессия.
5. **Сервер редактора живёт кодом на момент старта.** `vite.config.js` и
   `publishedHomeSceneKeys.js` он читает один раз; после коммитов, которые их
   меняют, перезапустить `editor` и перезагрузить вкладку.
6. **Два dev-сервера не делят `node_modules/.vite`**: временному серверу — свой
   `cacheDir`, иначе «504 Outdated Optimize Dep». По той же причине `npm ci`,
   `npm i` и `vite --force` вынимают кеш зависимостей из-под уже запущенных
   серверов — те продолжают отвечать, но отдают белый экран. Перед установкой
   и `--force` остановить чужие серверы, после — перезапустить их. Одного
   перезапуска мало: `?v=` у зависимостей после переустановки часто тот же,
   а содержимое другое, и уже открытые вкладки продолжают брать мёртвые
   модули из своего кеша (`immutable`) — им нужна жёсткая перезагрузка.
   Признак — «R3F: Hooks can only be used within the Canvas component!»
   при живом сервере, который в свежем профиле рисует нормально.
7. Телефон в той же сети — `npm run dev:lan`, тот же 41211: `http://<адрес-мака>:41211/?hud=1`.

Черновики со старых портов (7311 / 7312 / 4199): поднять старый порт один раз
(`npx vite --config vite.editor.config.js --port 7312 --strictPort`), открыть
`/home/edit`, нажать «В проект», на новом порту — «Откатить».

## 5. Лаборатория ассетов — без дублей

- Один вход: `asset-lab.html?collection=<id>`. Список коллекций — `src/asset-lab/assetCatalog.js`
  (номер, группа редактора, id, названия), компонент — в `assetRegistry.js`. Навигация
  `LabNav` по группам стоит на каждой странице; новая коллекция — строка в каталоге
  плюс компонент, номера идут подряд внутри групп.
- Коллекция стартует с опубликованной сцены (`getPublishedHomeSceneSettings()`) там,
  где у объекта есть настройки в редакторе; связь односторонняя, в сцену лаборатория
  не пишет. Лёгкая проверка связей — `npm run check:lab-links` (секунды, без браузера).
- Коллекция показывает модули продукта (`src/features/…`, `src/components/…`,
  `src/plants`, `src/tanker`), а не их копии. Лабораторный код — только студия,
  ракурсы, ползунки и пресеты. Копия продуктового модуля в `src/*-lab/` — ошибка,
  которую надо чинить импортом, а не синхронизацией.
- Стиль лаборатории (белая студия, типографика, панель) не меняется без Дениса.
  Оболочка и контролы одни на все коллекции — `LabShell.jsx` + `lab.css`;
  свой стиль, своя шапка или свой ползунок у коллекции — ошибка, чинить
  переносом в общую оболочку, а не новым файлом.

## 5.1. Проекты движка и справочник параметров

- Проект — это числа, а не модели: `<id>.json` = `{id, name, engine, kind?,
  created, updated, settings}`, где `settings` — плоский набор ключей сцены.
  Ассеты общие, лежат в `public/`, в проект не копируются (кроме моделей,
  импортированных в проект). Создаются и правятся из `/engine` на локальном
  сервере; редактор открывает проект по `/home/edit?project=<id>`. Проверка
  хранилища — `npm run check:projects`.
- **Дом данных один на все копии — `~/Ouroboros/{projects,presets}`**, вне
  репозитория (с 2026-09-24; `DDG_PROJECTS_DIR` переопределяет). Папки
  `projects/` и `presets/` в чекаутах — только README и старые копии, в git не
  попадают; перенос старых — `node scripts/migrate-projects-home.mjs`.
  Воркдерево со старым кодом читает свою папку, пока его код не обновлён.
- **Агент и проекты Дениса.** Смотреть — только без записи: `?preview=1` или
  `node scripts/render-view.mjs <проект> [камера]` (кадр в PNG, свой сервер и
  кеш). Править — файлом через хранилище (`projectStore.mjs`): открытый
  редактор подхватит правку, когда окно вернётся в фокус, а при одновременной
  правке сервер ответит 409 и редактор спросит, чью версию взять.
- **История и корзина** (с 2026-09-26, `projectStore.mjs`). Перед сменой сцены
  хранилище само кладёт версию с диска в `<проект>/history/<время>-<повод>.json`:
  при открытии в редакторе, первой записью после 10 минут без снимка, перед
  записью поверх чужой версии и перед возвратом; хранятся последние 50 и по
  одному на день. В проекте кнопка «Откатить» открывает «Историю проекта»
  (`FocusProjectHistory.jsx`) — сцена сайта в проект не подставляется.
  Удалённый проект уходит целиком в `~/Ouroboros/trash/projects/<id>--<время>/`,
  возвращается вкладкой «Корзина» меню проектов. Агент возвращает версию
  операцией (`projects.restore`, `POST /__projects/<id>/history/<снимок>`
  `{action: 'restore'}`), файлы истории и корзины руками не правит.
  Незнакомые поля сцены (их записала более новая версия движка) нормализатор
  сохраняет — в корне, в элементах списков и в снимках камер
  (`preserveUnknown.js`); миграция старого ключа — строка в
  `LEGACY_HOME_SCENE_INPUT_KEYS`. Запись несёт номер формата (`schema`,
  `STORE_SCHEMA` в `projectStore.mjs`): код поверх записи с номером новее своего
  не пишет (сервер отвечает 426, правки держит журнал восстановления). Поднимать
  номер, когда старый код прочтёт или сохранит новую запись неверно. Архив
  проекта одним файлом (`scripts/projectArchive.mjs`; меню проектов —
  «Сохранить архив» у карточки и «Открыть архив»; `npm run project:archive --
  export|import`): запись, папка проекта без истории, миниатюра и записи
  библиотек, которые сцена называет; при загрузке — свободное имя, свои записи
  библиотек не перезаписываются. Проверки — `check:projects`,
  `check:project-stability`.
- `kind: 'design'` — «Участок»: проектирование сада, без вещей сайта и моря
  (`site: true` в `sceneObjects.js`: они выключены и убраны из дерева, поиска
  и видимости). Без `kind` — обычный проект, как раньше. Модель в проекте
  помнит свою точку отсчёта (`origin`); «Заменить версию» ставит новую
  выгрузку туда же и переносит скрытые и удалённые части SketchUp по путям
  имён. Части модели — как в SketchUp: щелчок — компонент, двойной — внутрь,
  Esc — наружу, Delete — удалить (`sketchupModels[id].removed`: «Показать
  все скрытые» их не возвращает, только «Вернуть»); «Состав модели» — дерево
  с поиском, глазом и корзиной (`src/placed/SketchupOutliner.jsx`).
- Сайт проектом движка не является: у него свой черновик в localStorage и свои
  кнопки публикации. В меню проектов он стоит первым отдельной карточкой
  «Сайт» и открывает обычный `/home/edit`. Сцена сайта живёт в
  `publishedHomeSceneSettings.js`, и с 2026-09-23 её может занять любой проект:
  в проекте кнопка «На заглавную» пишет его сцену в этот файл («На сайт» — и
  сразу на GitHub), в меню проектов то же в контекстном меню карточки;
  `publishedHomeSceneSource.json` помнит, чей проект стоит на заглавной, и
  карточка «Сайт» это показывает. Прежнюю сцену сайта перед заменой
  сохранять проектом, чтобы Денис мог вернуть её той же кнопкой.
- Настройки движка (графика, плёнка и цвет, видимость, интерфейс, редактор,
  клавиши) открываются отдельным окном по шестерёнке в рельсе или через ⌘K, а не
  в правой панели. Пути узлов (`render/*`, `interface/ui`, `cursor/cursor`,
  `editor/settings`) не менялись — поиск, избранное и сохранённый выбор на них.
- Реестр связей объектов — `sceneObjects.js`: `roots` (имена в сцене), `sound`
  (дорожка), `newProject` (выключен в новом проекте). Выключенный объект
  пропадает отовсюду, кроме списка: дорожка молчит и не показывается, ракурс
  не предлагается. Новая связь — поле в строке объекта, не второй список.
  Принцип и план по живности — `docs/creatures-engine-2026-09-11.md`.
- Деталь — настроенный вариант одного объекта: `presets/<id>.json` =
  `{id, name, node, object, created, updated, values}`. Из деталей собирается
  новый проект; на сайт они не уезжают. Что входит в деталь, решает каталог
  контролов редактора для этого узла — второго списка не заводить.
  Открывается из редактора: ПКМ по объекту → «Детали объекта…» или ⌘K.
- `docs/engine-parameters.md` (и `.json` рядом) — что движок умеет: все
  параметры с подписями, пределами, единицами и заводскими значениями.
  Собирается из живого редактора: `npm run build:reference`. Руками не править;
  после добавления новых контролов пересобрать.
- Оболочка — `npm run app` (Electron, порт 41219 поднимается внутри неё).
  Проверка окна — `npm run check:app`.
- **Стабильная копия движка** (с 2026-09-26, `scripts/engineCopy.mjs`) —
  `~/Ouroboros/engine`, отдельный клон на коммите из `main`; установленное
  OUROBOROS.app запускается только из неё (`npm run app:install -- --replace`,
  `--here` — ярлык на свой чекаут для разработки). Обновление до `main` —
  `npm run engine:update`, откат — `engine:rollback`, состояние —
  `engine:status`; обновляет только при закрытом приложении и без правок в
  копии, зависимости ставит заново только при новом lock-файле. Агенты в
  копии не работают и не правят её; обновляют — только по просьбе Дениса,
  после влития в `main`. Проверка — `check:engine-copy`.
- **Служебные маршруты `/__*`** (проекты, публикация сцены и «На сайт»,
  библиотеки, ИИ, окружение) закрыты одной проверкой `scripts/localGuard.mjs`,
  первым плагином конфига: только этот компьютер (петля и имя хоста петли), тот
  же origin, не межсайтовый запрос и не тело простой HTML-формы. Новый маршрут
  своей проверки не заводит — он уже за этой. Проверка — `check:local-guard`.
- Библиотека растений — `~/Ouroboros/library/plants/<id>.json` (запись: имена,
  размеры, шт/м², календарь) и `<id>/card.webp`; в git и на сайт не уходит.
  Наполняется `scripts/import-plant-library.mjs` из библиотеки SketchUp
  Дениса, лианы — `scripts/climber-library.mjs` (лист — числами в
  `vineLeaves.js`, новая лиана — строка в таблице); записи правятся как
  обычный JSON. Посадки проекта (`src/planting`) хранят только id растений,
  правило цветника и мазки лиан — сами растения считают `fillBed.js` и
  `vines.js`, одинаково при каждом открытии. Работа с растениями — раздел
  «Растения» на левой рейке (узел «Посадки» — рабочее место с обзором,
  цветником и библиотекой); отчёт для заказчика — `/engine/report?project=<id>`.
  Картинка Дениса к растению — `<id>/photo.webp`, загружается из карточки.
  Сезоны по ИИ — `<id>/season-<фаза>.webp` (`scripts/plantSeasons.mjs`,
  кнопка в карточке растения; рисует только Денис, агент — на поддельном
  OpenAI); сцена берёт их по месяцу, без них — правка летней карточки.
  Грунт цветника — процедурный (`src/planting/bedGround.js`): кора с землёй с
  параллаксом, поверх поверхности модели по сетке высот цветника; опад и тень
  — от растений этого цветника, влага, выгорание коры и иней — от месяца.
  Газон — цветник `kind: 'lawn'` (инструмент «Газон»: тот же контур и та же
  поверхность модели): растений нет, покрытие само — трава с параллаксом
  (`src/planting/lawnGround.js`): плитка травинок, стрижка (полосы, клетка,
  ромбы, ровно, луг) — наклон травы по проходам, цвет по месяцу, без полива
  летом выгорает, опад и тень — от деревьев поштучно. В отчёте — площадь,
  рулон и семена; в сетке участка для электрики — «газон».
  Ветер сада — `src/planting/wind.js` (униформы общие, пишет `GardenWind`):
  посадки, лианы и 2D-растения модели качаются на ветре берега
  («Среда → Атмосфера → Ветер»); новое растение сада берёт `gardenSway` оттуда,
  своего ветра не заводить.
- Окружение «Участка» по адресу — дома, дороги, рельеф и деревья OpenStreetMap
  (`src/surroundings`, `scripts/surroundings.mjs`, узел «Ландшафт → Окружение»,
  решение — `docs/surroundings-2026-09-24.md`). Данные — файл проекта
  `projects/<id>/surroundings.json`, одна запись на строку; агент правит его
  как текст, пометив запись `edited`, `custom` или `hidden` (переживает новую
  загрузку), затем `node scripts/surroundings.mjs <проект> --touch`. Адрес и
  координаты — данные заказчика: их ключи не публикуются и в снимки камер не
  входят. Поворот карты — общий север участка (`northAngle`, `north.js`).
- Текстуры по ИИ и библиотека материалов — правый щелчок по модели SketchUp →
  «Сгенерировать / доработать текстуру…» (`src/materials`,
  `scripts/materials.mjs`, решение — `docs/ai-materials-2026-09-25.md`). ИИ
  рисует только цвет, остальные карты считаются из него (`materialMaps.mjs`).
  Библиотека — `~/Ouroboros/library/materials/<id>/`, в проекте —
  `modelMaterials` по имени материала SketchUp. Ключ OpenAI Денис вставляет сам
  («Настройки движка → API», связка ключей macOS); агент его не читает и не
  вставляет, проверки идут на поддельном сервере (`check:ai-materials`).
  Стекло моделей узнаётся само и отражает сцену с места камеры (`glass.js`,
  `GlassReflections.js`); библиотека на шаре и кубе и умолчания материалов —
  лаборатория, коллекция 18 «Материалы».
- Аннотации — пометки проектировщика поверх сцены (`src/annotations`, раздел
  «Аннотации» на рейке): пока отметки уровня (`annotationMarks[]`: x, y, z,
  `zero`, `ground`). Число — высота поверхности под отметкой от нулевой; слой
  находит её заново лучом сверху, когда модель пришла, заменена или сдвинута
  (только по своей поверхности: модели или плоскости). Только в редакторе и
  на генплане отчёта; на сайт не рисуются. Новый вид пометки — новый узел в
  группе `annotations`.
- Прогулка (кнопка «Прогулка», `src/walk`) — тот же человек и шаг, что у
  доски (`riderWalk.js`, `riderBody.js`), без физики: поза решается скелетом.
  Земля и стены — треугольники расстановки на входе (`walkGround.js`), логика
  и её проверка — `walkPlay.js` / `walk.check.js` (узел, без браузера).
  Камера от глаз — только пружиной второго порядка (`cameraFollow.js`): у
  шага есть изломы скорости, первое сглаживание их не убирает. Геймпад —
  раскладка и помощники доски (`usePlayKeys.js`), второй раскладки не заводить.
  Старт — `walkStart` (один на проект, `src/walk/settings.js`), ставится
  инструментом «Старт» (K) через `PlantingBrush` и узлом «Аннотации → Старт
  прогулки».
- Освещение сада (рейка «Освещение», `src/lighting`, решение —
  `docs/garden-lighting-2026-09-25.md`) — светильники и слой питания.
  Светильники — не источники three.js: их свет — световое поле
  (`lightField.js` + `gardenLightShader.js`, вставлено в
  `applyCloudShadowShader`, цена пикселя ограничена 16 светами клетки);
  корпуса — пачка экземпляров на тип (`housings.js`, `GardenLighting.jsx`);
  тени — атлас глубины по плиткам на свет (`gardenShadows.js`), рисуется при
  перестановке, не каждый кадр.
  Типы — заготовки `types.js` и изделия библиотеки
  `~/Ouroboros/library/luminaires/<id>.json` с происхождением каждого поля
  (паспорт / Денис / догадка), ценой (`price`) и картинкой `<id>/photo.webp`
  (без неё — схема корпуса по паспорту), фотометрия — `photometry.js`
  (IES/LDT или люмены и угол). Узел «Светильники» — рабочее место, как
  «Посадки»: библиотека по видам (`LUMINAIRE_KINDS`) и производителям и
  спецификация `luminaireSchedule` — одна для редактора и отчёта. Трассы, длины, нагрузки и ΔU не хранятся — их считает
  `electric.js` по сетке участка (`siteGrid.js`; редактор кладёт её в
  `projects/<id>/site-grid.json`); хранятся щитки, цепи и закреплённые трассы
  (`lightingRuns`). Агент работает через `node scripts/lighting.mjs <проект>
  report|lux|panels|circuits|apply`, не считая сам; утверждённые (`locked`)
  светильники без `--force` не трогает. Покрытия под материалами SketchUp —
  таблица `lightingSurfaces`; здание, где не копают, — только названное там.
  Ночь, в которой свет читается, — `hdriAtNight` (доля HDRI ночью, «Среда →
  HDRI»). Проверки — `check:garden-lighting`.
- ТЗ проекта — раздел «Проект» на рейке (только в проекте движка): заказчик,
  договор, сроки и свитки заданий по датам (`src/brief`, `sections/brief.jsx`).
  Файл — `projects/<id>/brief.json` в доме данных, не в `settings`: данные
  заказчика не публикуются, в снимки камер и в git не попадают. Задание —
  номер, текст, описание, приоритет, маркеры (узел редактора
  `greenery/topiary`, группа `lighting` или своё слово) и статус: `open` →
  `review` («ждёт проверки», с заметкой агента) → `done` (принял Денис).
  Когда Денис пишет «добавил задание» — `node scripts/brief.mjs` покажет, где
  открытые задания, `node scripts/brief.mjs <проект>` — их тексты и по
  маркерам файлы секций, с которых начинать. Сделанное — `node
  scripts/brief.mjs <проект> review <номер> --note "что сделано, коммит"`;
  `done` ставит только Денис. Файл руками не править — только операциями
  (`brief.js`: сервер, CLI и редактор). Проверка — `check:brief`.

## 6. Ядро рендера

Контракты света, CSM, AO, воды, сглаживания, FSR 1 и бюджета кадров —
[ddg-render-runtime](.agents/skills/ddg-render-runtime/SKILL.md). Перед изменением
этих систем читать соответствующий раздел скилла и указанный исходник. Настройки
качества участвуют в нормализации, публикации и снимках камер; эффективное
автокачество не должно перезаписывать авторские значения. Подробные результаты и
ограничения — в `docs/render-core-2026-09-07.md` и
`docs/render-upscale-2026-09-07.md`.

## 7. Камеры и сохранение

- Одна камера содержит два формата: Desktop и Mobile. «+» записывает текущий
  ракурс одинаково в оба; «Захватить» и FOV меняют только выбранный формат.
- Обычные и рабочие камеры хранят полный снимок сцены. Правки света, плёнки и
  постобработки принадлежат выбранной камере. Рабочие снимки остаются локальными;
  последняя обычная камера не должна получать изменения рабочего режима.
- Переходы — `editorCameraState.js`, запись — setter `useHomeSceneDraftSettings`.
  Не добавлять второй механизм сохранения снимков в рендере. Root публикации
  берётся из первой обычной камеры; звук общий и в снимки не включается.
- Сохранять существующие ID и авторские имена. Новые стандартные имена не должны
  повторять существующие. Старые рабочие pose-only данные мигрируют в два ракурса;
  дробный FOV не округлять. После reload сохраняются выбранная камера и формат.
- Регрессии этих контрактов — `npm run check:cameras`; визуальную проверку делать
  во встроенном браузере, операции с тестовыми камерами — на sandbox 41213.

## 8. Новая вода — перенос в продукт

- Новая вода живёт в `src/components/effects/water/` (`gerstnerWaves`,
  `GerstnerWaterSurface`, `waterShading`, `foamField`, `surfProfile`,
  `BreakingWaves`, `coastFrame`, `coastBreakLine`, `ShoreWater`) и в коллекции
  13 лаборатории. С 2026-09-08 `SeaWater` — единственная вода основной сцены.
  Старые `WaterSurface`, `FarWaterSurface` и их шейдеры лежат в `legacy/`
  вне активного графа импортов; старые водяные полосы ландшафта исключены.
  `useWaterRuntime` остаётся общей симуляцией ряби, проб и каустики, а не
  вторым визуальным слоем. Контракты курсора, лодки, рыб, чаек, кувшинок,
  скульптуры, отражений/рефракции, дна и водорослей, танкера, берегового звука,
  редактора/публикации и мобильного бюджета сохранять. Текущее состояние и
  ограничения — `docs/sea-only-2026-09-08.md` и летопись
  `docs/archive/handoff-log-2026.md`.
- Режим работы: математика и логика — агент, визуальная оценка — Денис в
  лаборатории; в конце ответа — список «что посмотреть» и вопросы. Кадры с
  GPU агент снимает для компиляции шейдеров и грубых дефектов, не для вкуса.
  Умолчания лаборатории — текущий тюнинг Дениса; его ползунки не переписывать.
- GLSL: `smoothstep` с обратными краями — неопределённое поведение (на Metal
  давал 0): только `1 − smoothstep`, веса окон через `clamp`. `coastHeight`
  в пиксельном шейдере запрещён — карта глубин (`coastGround`). `discard` в
  воде один (открытая вода у уреза), прозрачной открытую воду не делать.
- Лаборатория берёт файлы воркдерева живьём: любая отладочная подсветка видна
  Денису на его вкладке — только за URL-флагом и убирать в том же шаге.
- `npm run check:water` перед коммитом воды; сигнатуры `gerstnerDisplace` /
  `shadeWater` и юниформы шейдеров он сверяет по тексту.
