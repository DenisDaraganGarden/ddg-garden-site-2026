  **Прибой с закруткой** (идея Дениса по True Surf, 07.09): труба — нависание,
  карта высот (Герстнер, симуляция, `coastWave`) его не умеет по определению,
  поэтому обрушение — отдельный слой поверх Герстнера. Лента гребень×профиль
  (~200×24 вершин, 2–4 волны живут одновременно): профиль — сплайн
  подошва→стена→губа→завиток, у каждой точки гребня фаза обрушения 0…1,
  точка обрушения бежит вдоль гребня (пил); после схлопывания лента гаснет
  в бор, который пишет в буфер пены с памятью — одна система с пеной.

  толщина известна из профиля аналитически, без глубинных проходов.

## Что это

Главная страница `/` — 3D-сцена: пруд, лодка, скульптура-«голова», кувшинки, водоросли.
Редактор сцены — `/home/edit`. Стек: React + Vite + Three.js / react-three-fiber.
Запуск — через записи `.claude/launch.json`; карта портов и правила для агентов — в `AGENTS.md` (порты 41211–41215).

## Поток данных — три состояния, не путать

```
редактор → черновик (localStorage)  →  Publish  →  publishedHomeSceneSettings.js  →  главная
           ddg_home_scene_settings_v1            (файл в репозитории)
```

- **Черновик** живёт в браузере, пишется на каждое движение ползунка. Только редактор.
- **Publish** делает POST на дев-эндпоинт `/__home-scene/publish` (плагин в `vite.config.js`),
  который переписывает `publishedHomeSceneSettings.js`. **Работает только на localhost.**
- **Главная** читает опубликованный файл, черновик её не касается.

`publishedHomeSceneKeys.js` — список того, что вообще публикуется (сейчас 332 ключа).
Настройка, которой там нет, останется локальной: так живут `freeCamera`, `showPointerDebug`,
`showPerformanceHud`, `debugWireframe` — инструменты вьюпорта, а не свойства сцены.
Смоук-тест сверяет: каждый контрол редактора либо в этом списке, либо в его
`DEV_LOCAL_EDITOR_KEYS`. Забыть ключ нельзя — тест упадёт.

добавляется туда, а не отдельным ползунком.

берега добавляется в дефолты модуля и его `*_RANGES`, остальное подхватывается.

## Освещение: Sky + Sun + Moon

Одна таблица рассеяния питает всё, что обязано быть согласованным: видимое небо,
небо в отражении воды, заполняющий свет на материалах и цвет ключевого света.
Они не могут разойтись — это одни и те же числа.

| Файл | Что делает |
|---|---|
| `effects/sky/skyModel.js` | Физика: дуга солнца, воздушная масса, рассеяние, таблица неба. Чистый JS, без three — запускается в node |
| `effects/sky/skyModel.check.js` | `npm run check:sky`. Проверяет модель числами, а не скриншотом |
| `effects/shaders/skyShader.js` | Общий GLSL: `skyRadiance()` и `celestialBody()`. Импортируется небом И водой |
| `effects/water/skyEnvironment.js` | Мост в three: DataTexture + PMREM в `scene.environment` |
| `effects/water/SkyDome.jsx` | Видимое небо: три вершины на дальней плоскости |
| `effects/homeSceneLighting.js` | Контракт: раздел `sky` плюс ключевой свет, разложенный на цвет и уровень |

**Ключевые правила системы:**

- **Цвет солнца никто не выбирает.** Он получается из ослабления в воздухе: низкое
  солнце краснеет потому, что его свет прошёл больше атмосферы. `sunTint` — это
  цвет солнца *над* атмосферой, почти белый; всё тёплое возникает само.
- **Время суток ведёт высоту, азимут остаётся авторским.** В полдень дуга
  возвращает ровно заданные направление и высоту, поэтому старые сцены открываются
  там же, где были (`sunBearing` ← `moonAzimuth`, `sunNoonElevation` ← `moonElevation`).
- **Облачность — один физический факт, а не два ползунка.** Она забирает энергию у
  пучка и отдаёт её куполу, поэтому тень слабеет и смягчается сама, а кадр не темнеет.
- **`directShare`** — доля прямого света; ровно столько тень имеет право убрать.
  Считается в той же петле, что и таблица.
- **Тень доходит до воды** одной аппаратной выборкой (`sampler2DShadow`), без второй
  карты теней. Умножает блик, искры, солнечную дорожку и рассеяние в толще —
  поэтому мутная вода показывает тень **сильнее**, а не стирает её.
- **HDRI вспомогательный.** `envMode`: `sky` (по умолчанию, ничего не грузится),
  `sky+hdri`, `hdri`.

**Светильники** — группа «Свет» в редакторе: два источника, у каждого тело и цель,
оба двигаются манипулятором как отдельные объекты (как Corona Light). Угол конуса
180° превращает прожектор в точечный источник. «Участвует в отражениях» — это слой,
а не флаг видимости: снятая галочка убирает из зеркала и сам источник, и его свет.
Тени они не отбрасывают намеренно — вторая карта теней самое дорогое, что могла бы
попросить эта функция.

План целиком — `docs/lighting-plan.md`.

Аудит воды, курсора, волн, пены, погоды и ветра с замерами и порядком работ —
`docs/water-audit-2026-09-05.md`.

**Не проверено:** теневая выборка в собственном шейдере на живом iPhone. На
десктопе компилируется; это доказательство только для десктопа. Проверка:
`npm run dev:lan`, на телефоне открыть `http://<адрес>:41211/?hud=1` — в HUD строка
`SHADOW`. Если сцена вместо картинки показывает экран «WebGL не поддерживается» —
шейдер не скомпилировался, и запасной путь описан в плане (Фаза 3, `BasicShadowMap`).

## Грабли

- **Небо считается на процессоре один раз при загрузке.** Правка, которая заставит
  его пересчитываться каждый кадр, съест телефон. Ключ пересборки — `skyKey` в
  `skyEnvironment.js`, и он намеренно завязан на входы неба, а не на объект настроек.
- **Нормаль-мапа воды — не геометрический уклон.** Она усилена `normalStrength` ради
  освещения ряби. Строить по ней наклон объекта нельзя: кувшинки от этого встают дыбом.
  Наклон и высоту бери из height-field.
- **Вода непрозрачна и пишет глубину.** Всё, что оказалось ниже её поверхности, вырезается
  depth-тестом. Чтобы объект просвечивал сквозь воду, он должен попасть в проход преломления
  (`WaterReflections`) — и только подводной своей частью, иначе получишь его в кадре дважды
  и тёмную кайму. Глобальная плоскость отсечения так резать по волне не умеет и на кастомные
  шейдеры вообще не действует: рез делает сам шейдер объекта.
- **HMR ломает проходы отражений.** Правка модулей сцены может оставить чёрную воду или
  пустое преломление. Это артефакт разработки — лечится перезагрузкой страницы, к коду
  отношения не имеет. Прежде чем чинить «поломку», перезагрузи.
- **Скриншот из песочницы — плохой судья.** Проверять визуал лучше в браузере пользователя.
  Проверка кода = чистая компиляция + пустая консоль.
- **Постобработка включена** в опубликованной сцене. Без неё туман и лучи не
  работали вовсе — они живут только в этом проходе. Включить её удалось лишь после
  того, как в пост вернули тонмаппинг: three выкомпиливает его для рендера в
  текстуру, а весь кадр рисуется именно туда, поэтому тонмаппинга не было ни на
  одном пути. Рендерер теперь ACES Filmic.
- **Лучи видны, только когда солнце в кадре.** Обе авторские камеры смотрят вниз,
  поэтому при высоком солнце лучей не будет — это не поломка, а геометрия.
- **У береговой волны два тела.** `coastWave` в `terrain/terrainShader.js` (GPU: вода,
  пена, мокрый песок) и `sampleCoastWave` в `terrain/terrainModel.js` (CPU: лодка, пробы,
  посадка) обязаны быть одной формулой. Правишь одну — правь вторую, иначе лодка
  поплывёт не по той воде, что нарисована. Шум в волне поэтому не хэш, а суммы синусов.
  Та же пара у огибающей и мокрого песка: `coastWaveGain`/`coastWetnessAtHeight` и
  `sampleCoastWaveGain`/`sampleCoastWetness`.
- **Прибой без памяти.** Пена на песке не хранит историю: `coastSwashAt` считает
  аналитически, сколько секунд назад вода ушла с точки (арксинус огибающей плюс шаг
  Ньютона по скошенной волне) и где линия максимального заплеска. Поэтому телефон и
  десктоп рисуют одну и ту же пену. Кромка воды рваная одной функцией `coastEdgeRag`,
  на неё завязаны и отсечка воды, и кружево, и вырез рельефа в оптике.
- **«Рёбра под землёй» — юбки.** У каждой полосы рельефа (64 м вдоль берега) по краям
  висят вертикальные шторки: они прячут щели между соседними полосами разной
  детализации. Теперь они висят на глубину щели (0,45 м на ровном, до 5,6 м на обрыве),
  каркасный режим их не рисует (`drawRange` по `userData.topTriangles`), и внутри полосы
  три зоны сетки (шельф ¼ рядов, берег с обрывом полные ряды, плато ¼) со своими
  короткими юбками на стыках. Морф LOD считается по зонам, поэтому проверка
  `check:terrain` требует, чтобы счётчики колонок в полосах делились на два на каждый
  уровень, а срез плато (`plateauCut`) был один на весь берег.
- **Берег дорог пикселями, не треугольниками.** На камере у воды выключение рельефа
  снимало 19 мс из 28 при том, что рельеф это ~170k треугольников. Кадр держал
  фрагментный шейдер песка на весь экран: `coastHeight` (сорок трансцендентных) и
  прибой считались на каждый пиксель. Теперь высота грунта берётся из вершины, а
  прибой и мокрый песок считаются только в полосе q −26..12 м (в береговой воде пена
  тоже). Проходы оптики рисуют рельеф «двойником» на тех же буферах с четвертью
  треугольников. Любая новая функция в шейдере берега — сначала спросить, нужна ли
  она вне полосы у воды.
- **Рельеф режет себя в проходах оптики сам.** Общая плоскость отсечения на уровне
  спокойной воды не видит заплеск: песок под набегающей плёнкой не попадал в захват
  преломления, и вода у кромки показывала тёмное «тело» вместо песка. Теперь
  `uTerrainOptics` (1 преломление, 2 отражение) в `terrainMaterial.js` режет по
  `coastWave`, а чанк `clipping_planes_fragment` у рельефа заменён — глобальные
  плоскости на него больше не действуют.
- **Публикация только на localhost.** На задеплоенном сайте кнопка Publish неактивна.
- **Опубликованный файл — художественная работа Дениса.** Не откатывать и не переписывать
  руками.

## Проверки

| Команда | Что делает |
|---|---|
| `npm run lint` | ESLint |
| `npm run build` | Сборка |
| `npm run check:bundle` | Размеры и состав чанков по манифесту |
| `npm run check:sky` | Модель неба: дуга солнца, покраснение, энергия облачности |
| `npm run convert:models` | Пересобрать GLB из исходных OBJ |
| `npm run dev:lan` | Dev-сервер, видимый с телефона в той же сети |
| `npm run check:plants` | Куст и дерево: детерминизм, крепления, LOD-бюджеты, посадка на берегу |
| `npm run check:plants-parity` | Паритет трёх уровней растений в живой лаборатории (Playwright, нужен сервер `lab` или `PLANT_LAB_URL`): яркость карточки против геометрии на трёх дистанциях |
| `npm run check:terrain` | Рельеф: контракты высоты/нормали, контакт растений с грунтом |
| `npm run check:coast-contracts` | Стык воды и берега, таймлайн сцены, дальние чайки, LOD оптики |
| `npm run smoke` | Playwright: маршруты, WebGL-фолбэк, аудио, миграция черновика, покрытие publish-ключей, публикация end-to-end, память в долгой сессии, мобилка |

CI: `checks.yml` гоняет всё это на push и PR. `deploy-pages.yml` перед публикацией
прогоняет только быстрые детерминированные проверки (lint, build, check:bundle) —
браузерный смоук намеренно не может заблокировать деплой сайта.

## Замер на реальном устройстве

Профиль качества для слабых устройств написан, но на живом телефоне не проверялся —
эмуляция размера окна не эмулирует мощность GPU (в песочнице всё равно останется
десктопная видеокарта).

1. `npm run dev:lan` — Vite слушает на всех интерфейсах и печатает адрес в сети.
2. На телефоне в той же сети открыть `http://<адрес>:41211/?hud=1`.
3. `?hud=1` включает HUD прямо на главной (в dev-сборке): FPS, p95 кадра, память,
   треугольники, эффективное разрешение симуляции. Переключатель в панели редактора
   для этого не нужен — панелью на телефоне не поуправляешь.

Для сравнения, десктоп на M4 Max: 120 fps, 8.3 мс средний кадр, p99 10.8 мс,
42 вызова отрисовки, 852k треугольников — то есть упирается в частоту экрана.

**Смоуку нужна машина целиком** — перед запуском останови дев-серверы, иначе получишь
ложные падения из-за конкуренции за GPU.
