# Контентная платформа DDG — Payload CMS, подготовка без развёртывания

Этот каталог и `services/content-cms/` готовят закрытую редакторскую панель для сайта. Payload CMS хранит проекты, тексты RU/EN, теги, изображения, видео, черновики и историю изменений. PostgreSQL хранит записи, а сами загружаемые файлы остаются на собственном VPS. Эти файлы **ничего не запускают**, не создают DNS, не выпускают сертификаты и не меняют VPN.

## Что будет где лежать

```text
/srv/ddg-content/
  postgres/    # данные PostgreSQL; не редактировать руками
  uploads/     # изображения, видео, PDF и другие оригиналы Payload
  backups/     # локальные копии базы; нужна ещё одна копия вне VPS
```

`uploads/` не является публичной папкой Nginx. Файлы выдаёт только Payload по своим правилам: наружу — лишь медиа, которое редактор явно пометил как публичное; проекты наружу — лишь после публикации. Витрина сайта получает один безопасный JSON-манифест по адресу `/api/portfolio-manifest`; если панель временно недоступна, уже опубликованный сайт остаётся на своём резервном локальном списке.

## Что умеет панель

- Русский интерфейс с переключением языка, а тексты проекта и медиа ведутся отдельно на русском и английском.
- Проекты с текущими полями сайта: адрес, год, код, категория, имя/место/сотрудничество, координаты, тема, порядок, флаги портфолио и карты. В списках есть поиск по названию, месту, коду, адресу, имени файла, подписи и тегам.
- Упорядоченные изображения (только `image/*`) и отдельный упорядоченный список видео с постером и подписью. Видео пока не отправляется в старую витрину, поэтому не может случайно сломать галерею.
- Черновики, автосохранение, публикация по расписанию и до 100 версий проекта для восстановления.
- Вход по аккаунтам; управление аккаунтами и ролями доступно только администратору. Публичная регистрация полностью закрыта, а первый аккаунт создаётся одноразовой локальной командой до подключения внешнего шлюза.
- Лимит каждой загрузки 50 MiB; автоматически создаются `thumb`, `card` и `large` варианты изображений. Манифест берёт `large`, а если его нет — оригинал.

## Подготовка к первому запуску (когда будет отдельное разрешение)

1. На `ddg-bridge-01` создать `/srv/ddg-content/{postgres,uploads,backups}`. Каталог `uploads/` должен принадлежать UID/GID `10001:10001`, под которым работает Payload-контейнер; секреты и остальные каталоги остаются доступны только системному пользователю, запускающему Docker.
2. Скопировать `infra/content-platform/` и `services/content-cms/` на сервер, создать `.env` из `.env.example`, заменить каждое `CHANGE_ME` разным случайным значением и дать файлу режим `0600`. Пароль PostgreSQL генерируется hex-строкой: тогда он безопасно входит и в пароль базы, и в `DATABASE_URL` без неоднозначного URL-кодирования.
3. До production применить уже сгенерированную начальную миграцию к чистой тестовой PostgreSQL и проверить её подъём и откат. После проверки на VPS сначала запускается только PostgreSQL, затем та же миграция командой `docker compose --profile maintenance run --rm payload-migrate`. Новые миграции никогда не генерируются прямо на рабочем production-сервере: они создаются и проверяются в отдельной тестовой БД, коммитятся и только затем запускаются в production. Maintenance-контейнер не имеет порта и не запускается обычной командой `up -d`.
4. Пока основной Payload-контейнер ещё не запущен, создать первого администратора локальной командой `docker compose --profile maintenance run --rm -e BOOTSTRAP_ADMIN_EMAIL -e BOOTSTRAP_ADMIN_PASSWORD payload-bootstrap`. Команда откажется работать, если в базе уже есть хотя бы один пользователь. После этого можно поднять Payload, который слушает только `127.0.0.1:3000`; PostgreSQL остаётся без опубликованного порта. Внешний Nginx дополнительно блокирует встроенный маршрут первой регистрации, поэтому он не откроется даже при ошибочно пустой базе.
5. Загрузить тестовую фотографию, сделать её публичной, создать проект-черновик, опубликовать его, проверить манифест и восстановление одной версии. Лишь затем импортировать реальные материалы.

## Публикация без смены VPN

На `ddg-bridge-01` порт `443` занят VPN и его не трогаем. Подготовлен отдельный будущий шлюз на `nigrita`:

- `admin.denisdaragan.com` — полная закрытая панель Payload через обратный SSH-туннель.
- `content.denisdaragan.com` — отдельный публичный узкий маршрут. Он пропускает только `GET/HEAD/OPTIONS` для `/api/portfolio-manifest` и публичных файлов `/api/media/file/...`; любая другая попытка получает отказ.

Оба домена идут в один loopback-туннель `nigrita:127.0.0.1:18055` → `ddg-bridge-01:127.0.0.1:3000`. Ни один из шаблонов не включён. Никаких ключей, сертификатов и DNS в репозитории нет.

Манифест передаёт относительные пути медиа и отдельный `PUBLIC_MEDIA_ORIGIN`, то есть будущий `https://content.denisdaragan.com`, а не адрес админ-панели. Это соответствует контракту сайта, позволяет держать редактор закрытым и безопасно выдавать изображения. Один повреждённый проект или закрытый файл логируется и пропускается локально, не обрушая весь опубликованный список; сама публикация заранее запрещается, пока связанные файлы не отмечены публичными.

## Первый перенос существующего портфолио

Сейчас в исходном реестре сайта 6 записей и 23 изображения. Первый импорт выполняется только в отдельной тестовой БД и состоит из трёх проверяемых частей: сверка 6 адресов проектов, копирование 23 файлов с проверкой имени и размера, затем сопоставление каждого файла с проектом в исходном порядке. Будущий импортёр должен искать существующие записи по `slug`, а файлы — по имени, поэтому повторный запуск не создаёт дубли; реальная запись — только с явным `--execute`, до него — dry-run и список различий. Автоматический импортёр намеренно не добавлен в эту заготовку: его нельзя честно проверить без работающей тестовой PostgreSQL и реальной проверки Payload Local API. До такой проверки существующая витрина продолжает читать свой локальный реестр.

## Резервные копии

`scripts/backup.sh` по умолчанию только показывает будущую операцию. Реальная копия создаётся только с `--execute`. Скрипт делает сжатую логическую копию PostgreSQL во временный файл, проверяет его `gzip -t`, затем атомарно переименовывает. Существующие бэкапы, `uploads/` и данные он не перезаписывает и не удаляет.

Одна копия на VPS недостаточна: нужно отдельно и регулярно копировать **и базу, и `/srv/ddg-content/uploads/`** на независимое зашифрованное хранилище. Восстановление тестируется только на отдельной тестовой БД, не на рабочей.

## Проверки до развёртывания

```bash
docker compose --env-file .env config
./scripts/backup.sh
```

Это проверки без запуска: первая валидирует итоговую конфигурацию, вторая обязана закончиться `Dry run only`. Начальная migration сгенерирована самой версией Payload/Drizzle, закреплённой в lock-файле; перед production её всё равно нужно применить к чистой тестовой PostgreSQL, проверить схему, создание первого администратора и откат.
