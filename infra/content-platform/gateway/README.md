# Закрытый шлюз редактора между VPS — только шаблоны

Этот каталог описывает будущий путь к редактору:

```text
Редактор: https://admin.denisdaragan.com (Nginx на nigrita, отдельный SNI-vhost)
Публичный контент: https://content.denisdaragan.com (тот же Nginx, отдельный строго ограниченный SNI-vhost)
  -> 127.0.0.1:18055 на nigrita
  -> обратный SSH-туннель
  -> 127.0.0.1:3000 (Payload на ddg-bridge-01)
```

Здесь нет ключей, сертификатов, паролей и команд, которые что-либо запускают. Само наличие файлов не меняет ни один сервер. До отдельного подтверждения не создавать DNS-запись, не выпускать сертификат, не копировать файлы и не включать unit/vhost.

## Границы безопасности

- `ddg-bridge-01` только **исходяще** подключается к `nigrita:2222`; Payload остаётся на `127.0.0.1:3000`.
- Туннель слушает на `nigrita` строго `127.0.0.1:18055`: он не доступен из интернета, даже при широкой firewall-политике.
- Пользователь `ddg-content-tunnel` на `nigrita` принимает только один ключ и только этот обратный порт. Ему запрещены пароль, терминал, команды, агент, X11 и прямые TCP-переадресации.
- `admin.denisdaragan.com` — отдельный Nginx SNI-vhost на уже существующем `:443`; он не занимает `:443` отдельным процессом и не относится к VPN на `ddg-bridge-01`.
- `content.denisdaragan.com` пропускает только `GET`, `HEAD` и `OPTIONS` к `/api/portfolio-manifest` и `/api/media/file/...`; всё остальное возвращает `404` или `405`.
- Ни один шаблон Nginx не открывает `uploads/` как статическую директорию.

## Состав

- `ddg-bridge-01/ddg-content-tunnel.service` — systemd unit, поддерживающий один исходящий SSH-туннель.
- `ddg-bridge-01/ssh-config` — закрепляет ключ хоста и запрещает интерактивное поведение клиента.
- `nigrita/sshd_config.d/99-ddg-content-tunnel.conf` — ограничение tunnel-пользователя на SSH-сервере.
- `nigrita/authorized_keys.example` — единственная строка ключа, которую помещают в `~ddg-content-tunnel/.ssh/authorized_keys` после подстановки **публичного** ключа.
- `nigrita/nginx/admin.denisdaragan.com.conf.template` — полный закрытый SNI-vhost панели.
- `nigrita/nginx/content.denisdaragan.com.conf.template` — узкий публичный SNI-vhost манифеста и медиа.
- `nigrita/nginx/00-ddg-content-rate-limits.conf.template` — общие ограничения частоты входа, запросов панели и публичных файлов; устанавливается в `conf.d` вместе с vhost-файлами.

## Ручное включение после отдельного согласования

Эти действия намеренно не автоматизированы. Они затрагивают два VPS и публичный домен, поэтому перед каждым этапом нужно сделать резервную копию существующей конфигурации и проверить её владельцем сервера.

1. На `nigrita` создать системного пользователя `ddg-content-tunnel` без пароля и без интерактивного входа. Внести SSH Match-конфигурацию и один публичный ключ из примера. Перед перезагрузкой SSH проверить конфигурацию командой `sshd -t` в отдельной уже открытой сессии.
2. На `ddg-bridge-01` создать отдельный закрытый ключ только для этого туннеля. Закрытый ключ должен принадлежать сервисному пользователю `ddg-content-tunnel-client` и иметь режим `0600`; каталог — `0700`. Конфигурация и `known_hosts` могут быть root-owned, но должны оставаться читаемыми сервисному пользователю. Получить и **сверить по доверенному каналу** host key `nigrita`, затем записать его в выделенный `known_hosts`; не применять `StrictHostKeyChecking=no`.
3. На `ddg-bridge-01` установить unit и включить его только после проверки, что Payload отвечает локально на `127.0.0.1:3000/api/health`. Убедиться на `nigrita`, что `127.0.0.1:18055` существует, а `0.0.0.0:18055` — нет.
4. На `nigrita` установить общий rate-limit-файл, подставить реальные пути к уже выпущенному сертификату в оба Nginx-шаблона. Они используют существующие Certbot-параметры TLS сервера. Проверить `nginx -t` и только затем reload Nginx. Это добавляет SNI-имена к существующему процессу, а не запускает второй процесс на `:443`.
5. Только после этого добавить DNS для `admin.denisdaragan.com` и `content.denisdaragan.com`, проверить роли, загрузку тестового файла, узкое публичное API, резервную копию и откат. Переключение сайта на новый манифест — отдельный этап.

Если `nigrita` недоступен, редактор перестанет быть доступным извне, но сайт, VPN и сами данные на `ddg-bridge-01` продолжают работать. Это gateway для административной панели, а не замена резервным копиям и не CDN.
